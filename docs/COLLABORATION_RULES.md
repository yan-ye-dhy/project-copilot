# Project Copilot：项目开发与学习协作规则

生效日期：2026-10-11。根据用户最新指令建立，作为后续每日工作的长期规范。与此前“Codex负责全部逐段带读”“不执行远程push”“终端复现可选”等约定冲突时，以本规范为准。历史代码、测试证据和学习材料保留。

项目目标仍是研发知识与工单协作智能体，面向AI应用/Agent实习准备：用户最终能理解、修改、扩展项目，并介绍架构和实现。技术路线、每日任务、工时及核心验收见 [DEVELOPMENT_PLAN.md](DEVELOPMENT_PLAN.md)；实际记录见 [DEVELOPMENT_LOG.md](DEVELOPMENT_LOG.md)。

## 1. 三方职责

| 参与方 | 主要职责 | 交付或反馈 |
| --- | --- | --- |
| Codex | 按当天计划实现，调整必要结构，运行必要自动测试/静态与集成检查，修复问题，提交推送，提供开发摘要与测试指导 | 代码、真实验证记录、GitHub commit与8项开发报告；用户主动要求后的单步手动带练 |
| ChatGPT | 阅读GitHub最新代码和当天commit，解释代码、语法、库/框架API，梳理调用与数据传递，分析设计取舍和历史模块关系 | 代码与架构教学、整体运行链、知识点和面试经验 |
| 用户 | 通过ChatGPT学习，确认理解后回Codex亲自运行功能、观察结果和反馈问题 | 学习确认、真实命令/输出/截图、问题及理解反馈 |

Codex开发前后简要说明方案、重要设计和新增依赖，方便交接；系统逐行教学主要由ChatGPT承担。用户直接要求解释某处代码时，可回答该问题，不因此自动进入手动测试或新的开发任务。

## 2. 每日顺序与范围

1. 用户开启某个Day后，Codex读取当前结构、开发计划、日志和Git状态，确认当天目标与涉及文件。
2. Codex完成当天一个主要增量，执行相关自动验证并修复失败，检查diff，提交并推送约定GitHub分支，输出开发报告。
3. 用户把报告、commit和代码交给ChatGPT，学习功能、实际执行链和设计理念。
4. 学习后，用户主动发送“开始今天的手动测试”，或同等明确的手动测试请求。
5. Codex指导用户亲自操作；一次只给一个环节，等待实际结果后确认和继续。
6. 记录当天学习与手动验证状态。A/B阶段都完成后，等待用户要求才进入下一Day。

当天开发不需要每写几行就暂停等待系统教学，但应保持增量小、职责清楚、命名合理、重要逻辑有适量注释。保留必要工程质量，不做多Agent、微服务等范围外扩展；发现计划问题先说明调整原因，不擅自扩大当天范围。

开发、ChatGPT学习、手动测试与记录都计入计划的90～150分钟项目预算，可分不同时间段完成；达到约2.5小时则记录状态并顺延，不压缩必要验证，也不追赶下一Day。

## 3. 自动验证和人工操作分别记录

Codex在开发期间可以运行与变更相关的自动化测试、静态检查，以及必要的自动启动/请求/隔离存储集成验收，不需要等待手动测试触发。所需模型调用仍遵守开发计划第8.3节的费用与授权规则。

每条验证记录包括执行者、环境、实际命令、目标/预期、实际结果、失败原因及未解决问题。未执行、mock、真实服务/模型、用户操作分别标明，不得相互代替或声称未验证的检查通过。

Codex自行运行HTTP、数据库、RAG或Agent验收，仍属于助手验证；不得代替用户的学习后手动验证。未收到用户主动开始手动测试的请求前，只提供开发交接和测试范围提示，不进入测试教学或安排用户操作。

人工gold标注、证据支持判定、业务确认等原计划中的必要人工环节仍保留。它们的实际进度单独记录，不把协作分工变化当成自动化替代这些验收的授权。

## 4. Git提交、推送与交接

- 每次审核diff和文件清单，只提交当天真实改动，排除.env中的密钥、密码、Token、私密资料、缓存、虚拟环境及持久数据。
- 使用新项目独立Git历史；原项目始终只读，不替其整理或提交已有改动。
- 用户已授权后续每日提交和常规推送到约定GitHub仓库/分支。每次核实目标和当前分支；不强推、不重写提交历史、不删除重要数据。
- 远端地址或分支尚不明确时，完成不依赖远端的工作、记录待同步，并请求缺失信息；不猜测仓库、不把旧参考仓库当成新项目远端。
- 推送失败时记录真实原因和可处理的下一步，不声明GitHub已同步。认证信息通过正常工具/终端流程处理，不写进仓库、日志或远端URL。
- 报告引用实际commit、分支、推送状态和 `https://github.com/<owner>/<repo>/commit/<完整commit>` 链接；目标未知或未推送时明确写“暂无可确认的GitHub提交链接”。
- 日报可随真实任务保存为 `docs/reports/DAY_<N>.md`，到对应任务再创建；报告与提交分别记录，不为规则适配伪造Day成果或自引用commit ID。

2026-10-11适配时快照：本地分支main，有D1及教学文档的真实提交；尚无remote。用户说明尚未创建GitHub仓库并要求指导创建，已明确选择Public，公开代码与项目文档。首次关联前需完成空仓库创建并获得实际地址，后续默认沿用当前main，用户指定其他分支时优先。此快照不替代每次任务前的Git核实。

同日首次同步后，约定仓库为 [yan-ye-dhy/project-copilot](https://github.com/yan-ye-dhy/project-copilot)，可见性Public；`origin`地址为 `https://github.com/yan-ye-dhy/project-copilot.git`，本地main跟踪origin/main。Git仅在本项目配置中使用已登录的GitHub CLI凭据助手，不保存Token到仓库。实际推送与当前A/B状态见开发日志。

## 5. 固定开发报告

每个Day开发结束时使用下面8项，给ChatGPT提供清晰入口；设计部分仅做定位摘要，完整教学交ChatGPT。未完成项如实填写。

### 【Day N 开发报告】

**1. 今日开发目标**

当天目标、实际完成范围和未完成内容。

**2. 新增和修改的文件**

分别列新增/修改路径和职责；涉及删除时说明真实原因。

**3. 核心实现内容**

主要模块、类、函数、API、数据库结构或实验配置的变化。

**4. 关键设计决策**

方案及原因、新依赖用途、重要取舍；不展开逐行教学。

**5. 自动测试结果**

实际执行命令、环境、通过/失败、限制和未解决问题；区分自动与用户验证。

**6. GitHub 提交信息**

实际commit ID、分支、推送结果、可访问提交链接；失败或待推送明确填写。

**7. 后续学习提示**

当天最值得向ChatGPT学习的3～5个知识点，指向相关代码、调用关系或设计问题。

**8. 下一步计划**

当前学习/手动验证的待办与下一Day目标；写明等待用户主动开始手测或要求下一Day，不自动执行。

## 6. 手动测试教学模式

**触发：用户主动要求开始当天手动测试。** 收到请求后先核对正在学习的Day、功能范围、自动验证记录与环境，不擅自重开其他任务。

先简要介绍本日测试目标及各测试对应的代码/业务。随后每次只指导一个环节：

1. 测试目的，以及验证的模块或逻辑。
2. 前置条件、需要的环境和服务。
3. 当前一步的具体操作或命令。
4. 简要解释新工具、命令参数或请求字段。
5. 预期输出、HTTP响应、数据库变化或中间状态。
6. 成功判断，以及失败时先检查的文件、日志和服务。
7. 等待用户反馈结果或截图，再确认、排查或给出下一环节。

复杂操作分步进行，不一次发送大量命令。让用户观察输入、处理中间数据/日志/状态和输出；数据库、检索、工具执行等不能只让用户跑一条测试命令就结束。Codex可提供自动测试证据作参考，用户的手动运行由本人完成。

## 7. 完成标准与当前状态

| 阶段 | 完成标准 |
| --- | --- |
| A 开发完成 | 当天功能完成；必要自动验证实际执行，限制如实记录；代码推送GitHub；8项开发报告生成 |
| B 学习与验证完成 | 用户通过ChatGPT理解代码；主动回Codex并亲自手动测试；结果符合预期或问题明确记录；基本能解释运行逻辑 |

“代码已写”“本地commit”“自动测试通过”“用户一次请求成功”分别只证明对应部分。只有A/B都完成才默认具备进入下一Day的条件；仍等待用户明确要求，不自行推进。

适配时的D1状态：工程实现及已有助手验收完成；GitHub尚未配置，不能按新规范登记完整A阶段；用户已展示默认健康请求成功截图，但ChatGPT学习完成与完整手动验收尚未确认，B阶段未登记完成。本次仅保存规范和更新引用，GitHub创建指导属于仓库准备，不是D2开发，也不是“开始今天的手动测试”的触发。
