# Project Copilot：项目开发与学习协作规则

生效日期：2026-10-11。根据用户最新指令建立，作为后续每日工作的长期规范。同日追加：Git提交和推送由用户在Codex指导下亲自操作，替代此前Codex自动提交/推送约定。与此前“Codex负责全部逐段带读”“不执行远程push”“终端复现可选”等约定冲突时，以本规范为准。历史代码、测试证据和学习材料保留。

项目目标仍是研发知识与工单协作智能体，面向AI应用/Agent实习准备：用户最终能理解、修改、扩展项目，并介绍架构和实现。技术路线、每日任务、工时及核心验收见 [DEVELOPMENT_PLAN.md](DEVELOPMENT_PLAN.md)；实际记录见 [DEVELOPMENT_LOG.md](DEVELOPMENT_LOG.md)。

## 1. 三方职责

| 参与方 | 主要职责 | 交付或反馈 |
| --- | --- | --- |
| Codex | 按当天计划实现，调整必要结构，运行必要自动测试/静态与集成检查，修复问题，审核Git改动并指导用户提交推送，提供开发摘要与测试指导 | 代码、真实验证记录与8项报告；核实用户提交/推送结果；用户主动要求后的单步手动带练 |
| ChatGPT | 阅读GitHub最新代码和当天commit，解释代码、语法、库/框架API，梳理调用与数据传递，分析设计取舍和历史模块关系 | 代码与架构教学、整体运行链、知识点和面试经验 |
| 用户 | 在Codex指导下亲自执行Git提交/推送；通过ChatGPT学习，确认理解后回Codex亲自运行功能、观察结果和反馈问题 | 实际Git操作结果、学习确认、真实命令/输出/截图、问题及理解反馈 |

Codex开发前后简要说明方案、重要设计和新增依赖，方便交接；系统逐行教学主要由ChatGPT承担。用户直接要求解释某处代码时，可回答该问题，不因此自动进入手动测试或新的开发任务。

## 2. 每日顺序与范围

1. 用户开启某个Day后，Codex读取当前结构、开发计划、日志和Git状态，确认当天目标与涉及文件。
2. Codex完成当天一个主要增量，执行相关自动验证并修复失败，检查diff，提供开发报告草稿，Git状态明确填“待用户提交/推送”。
3. Codex逐步指导用户亲自提交并推送约定GitHub分支，核对实际结果后补全报告中的commit、分支、推送状态和链接。
4. 用户把报告、commit和代码交给ChatGPT，学习功能、实际执行链和设计理念。
5. 学习后，用户主动发送“开始今天的手动测试”，或同等明确的手动测试请求。
6. Codex指导用户亲自操作；一次只给一个环节，等待实际结果后确认和继续。
7. 记录当天学习与手动验证状态。A/B阶段都完成后，等待用户要求才进入下一Day。

当天开发不需要每写几行就暂停等待系统教学，但应保持增量小、职责清楚、命名合理、重要逻辑有适量注释。保留必要工程质量，不做多Agent、微服务等范围外扩展；发现计划问题先说明调整原因，不擅自扩大当天范围。

开发、用户Git操作、ChatGPT学习、手动测试与记录都计入计划的90～150分钟项目预算，可分不同时间段完成；达到约2.5小时则记录状态并顺延，不压缩必要验证，也不追赶下一Day。

## 3. 自动验证和人工操作分别记录

Codex在开发期间可以运行与变更相关的自动化测试、静态检查，以及必要的自动启动/请求/隔离存储集成验收，不需要等待手动测试触发。所需模型调用仍遵守开发计划第8.3节的费用与授权规则。

每条验证记录包括执行者、环境、实际命令、目标/预期、实际结果、失败原因及未解决问题。未执行、mock、真实服务/模型、用户操作分别标明，不得相互代替或声称未验证的检查通过。

Codex自行运行HTTP、数据库、RAG或Agent验收，仍属于助手验证；不得代替用户的学习后手动验证。未收到用户主动开始手动测试的请求前，只提供开发交接和测试范围提示，不进入测试教学或安排用户操作。

人工gold标注、证据支持判定、业务确认等原计划中的必要人工环节仍保留。它们的实际进度单独记录，不把协作分工变化当成自动化替代这些验收的授权。

2026-10-17补充：用户实际核对后，可以按明确题号范围批量确认人工gold，无需逐题重复书面依据；仅存疑或需要修改的题补充说明。Codex根据用户明确反馈登记复核状态，不能依据程序通过或AI草稿自行确认。

## 4. Git提交、推送与交接

- Codex每次审核diff和文件清单，提供具体暂存路径与提交说明；用户只提交当天真实改动，排除.env中的密钥、密码、Token、私密资料、缓存、虚拟环境及持久数据。
- 使用新项目独立Git历史；原项目始终只读，不替其整理或提交已有改动。
- 默认由用户亲自执行`git add`、`git commit`、`git push`等Git写操作，Codex不自动代执行，本次规则文档也保持待用户提交。只有用户针对当前操作明确要求代执行时，才按该次授权执行。
- Codex可以只读核实status/diff/log/remote；每次先核实目标和当前分支，不强推、不重写提交历史、不删除重要数据。
- Git指导一次只推进一个环节：检查改动 → 暂存指定文件并核对 → 本地commit → push → 确认远端同步。每步说明用途、关键参数、预期与排查方法，等待用户反馈再继续。
- Git提交指导属于开发交接，可在开发与自动验证结束后进行；“开始今天的手动测试”用于学习后的功能验收，两者分别记录，不相互触发。
- 远端地址或分支尚不明确时，完成不依赖远端的工作、记录待同步，并请求缺失信息；不猜测仓库、不把旧参考仓库当成新项目远端。
- 推送失败时记录真实原因和可处理的下一步，不声明GitHub已同步。认证信息通过正常工具/终端流程处理，不写进仓库、日志或远端URL。
- 提交前报告注明待用户提交/推送；核实用户实际操作后，引用真实commit、分支、推送状态和 `https://github.com/<owner>/<repo>/commit/<完整commit>` 链接。仅有本地commit时不能标已同步，未推送时明确写“暂无已同步的GitHub提交链接”。
- 最终Git信息可在会话中补充，不要求报告文件追填自己的提交ID；若补写文件产生新改动，也交用户处理，不由Codex自动追加提交。
- 日报可随真实任务保存为 `docs/reports/DAY_<N>.md`，到对应任务再创建；报告与提交分别记录，不为规则适配伪造Day成果或自引用commit ID。

## 5. 固定开发报告

每个Day开发结束时使用下面8项，给ChatGPT提供清晰入口；设计部分仅做定位摘要，完整教学交ChatGPT。未完成项如实填写。

### 【Day N 开发报告】

**1. 今日开发目标**

当天目标、实际完成范围和未完成内容。

**2. 新增和修改的文件**

分别列新增/修改路径和职责；涉及删除时说明真实原因。

**3. 核心实现内容**

主要模块、类、函数、API、数据库结构或实验配置的变化。

**4. 关键设计决策**

方案及原因、新依赖用途、重要取舍；不展开逐行教学。

**5. 自动测试结果**

实际执行命令、环境、通过/失败、限制和未解决问题；区分自动与用户验证。

**6. GitHub 提交信息**

实际commit ID、分支、用户推送结果、可访问提交链接；尚未操作时填待用户提交/推送，失败如实记录，不预填提交ID或成功状态。

**7. 后续学习提示**

当天最值得向ChatGPT学习的3～5个知识点，指向相关代码、调用关系或设计问题。

**8. 下一步计划**

当前学习/手动验证的待办与下一Day目标；写明等待用户主动开始手测或要求下一Day，不自动执行。

## 6. 手动测试教学模式

**触发：用户主动要求开始当天手动测试。** 收到请求后先核对正在学习的Day、功能范围、自动验证记录与环境，不擅自重开其他任务。

先简要介绍本日测试目标及各测试对应的代码/业务。随后每次只指导一个环节：

1. 测试目的，以及验证的模块或逻辑。
2. 前置条件、需要的环境和服务。
3. 当前一步的具体操作或命令。
4. 简要解释新工具、命令参数或请求字段。
5. 预期输出、HTTP响应、数据库变化或中间状态。
6. 成功判断，以及失败时先检查的文件、日志和服务。
7. 等待用户反馈结果或截图，再确认、排查或给出下一环节。

复杂操作分步进行，不一次发送大量命令。让用户观察输入、处理中间数据/日志/状态和输出；数据库、检索、工具执行等不能只让用户跑一条测试命令就结束。Codex可提供自动测试证据作参考，用户的手动运行由本人完成。
