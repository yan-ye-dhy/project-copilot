# 消息队列升级第二批开发报告

## 1. 目标

为新登记的 PERSONAL_DEMO RAG/Agent 任务增加证据驱动的有界恢复，保留历史 unknown、费用不确定性、原额度和幂等身份。Broker 重投不等于授权重新调用模型。

## 2. 文件

- `db/recovery.py`、`0018_job_recovery.py`：恢复元数据、不可变旧执行快照、跨 attempt 提案身份、限长步骤收据。
- `services/job_recovery.py`：新任务登记、原始时限、累计预算、物理证明核查、恢复协调及有界公平扫描。
- `services/job_steps.py`：意图先提交、标准化结果收据、缓存再授权、步骤幂等和容量限制。
- `services/execution_slots.py`、`agent/proposals.py`：旧 token fencing、完整归档后轮换当前证明、复用原提案。
- Worker、MQ协调器、provider accounting、API和配置：登记/领取/完成/空闲检查接入。
- `services/public_maintenance.py`：只读检查恢复摘要；显式清理已结算内容收据，保留业务和执行证据。
- 新增隔离PG、配置和消费线程维护测试。

## 3. 核心实现

仅新任务且开关显式启用时登记协议2；原记录不回填。恢复需要当前发布/用户/Session/Context/授权窗口、不可变 lease inode、已结束本地执行、零开放供应商操作及无供应商终态不确定性。满足条件后，先在同一事务归档旧证明并 fencing，再安排第2代 Outbox；后续领取核对归档，才轮换当前 token。

同一个 logical job 最多两个实际执行 attempt，额度 reservation 和幂等键不变。绝对执行时限从第一次领取开始，停机时间计入；provider、模型和工具累计预算不因恢复清零。没有模型发起的本地失败可自动恢复；已发生模型请求且缺少结果时，需要明确的重复模型策略，仍不能覆盖 provider_uncertain 或活跃执行。

提案由唯一 `(job_id, operation_key)` 绑定原 action；跨 attempt 只能复用它，内容指纹不匹配时拒绝。确认继续由独立接口、事务行锁和原创建唯一键控制，模型不获得确认权限。

## 4. 设计决策

保留现有当前执行证明作为指针，轮换前归档完整不可变快照，避免重写过去的执行事实。恢复扫描按最后检查时间轮转，永久阻塞任务不会饿死后续候选。消费维护与实际工作使用同一业务 executor，broker I/O 独立维护心跳；不增加GPU并行度。

步骤收据每条最多256KiB、每任务最多256条及4MiB。结果复用仍核对当前身份、配置、索引及来源权限。收据是可恢复内容，不等于供应商账单或完整原始响应；未知 usage 保持未知。

## 5. 自动验证

Codex使用隔离真实PG、模型替身及独立RabbitMQ测试；没有调用付费模型或修改演示库。

- 相关PG回归115 passed（78.55秒），覆盖恢复/步骤/分发、既有执行证明、审批与个人额度。
- 步骤收据容量/竞争等30项验证通过；与上项有重叠，不相加作为唯一总数。
- 既有维护/历史人工退役51 passed，新内容保留策略2 passed。
- 用量范围及恢复协调9 passed；复核发现只保存新attempt用量会少计旧消耗，已修复为保留旧收据、无法证明总量时保持unknown，缓存结果不重复相加。
- 配置/传输/信号回归22 passed；真实broker空闲维护12秒后发送/消费通过。
- 完整离线Python回归1958 passed、491 skipped、0 failed（105.38秒）；随后新增usage回归已单独通过。最终统一回归在第三批完成后执行，远端CI以PR实际结果为准。

测试中的用户/发布授权和供应商响应均为隔离合成数据；没有将其登记为真实用户操作或正式发布证据。
